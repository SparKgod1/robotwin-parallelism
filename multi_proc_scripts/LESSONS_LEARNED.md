# 多机并行数据采集：经验总结

## 1. NFS 上的 fcntl.flock 是性能杀手

**问题**：每个 episode 渲染完都对共享的 `scene_info.json` 加排他锁，640 个 worker 串行等待。

**表现**：单卡 60 ep/min → 多机并行后 1 ep/h/worker（3600 倍降速）。

**解决**：去掉共享文件锁，改为每个 episode 写独立小文件（`_scene_info/episode_N.json`），最后 finalize 阶段合并。

**原则**：NFS 上绝不在热路径使用阻塞锁。如果必须共享状态，用"写独立文件 + 最终合并"模式。

## 2. GPU 并行度不是越高越好

**问题**：每 GPU 4 个渲染进程，显存和计算互相抢占，总吞吐反而低于每 GPU 1-2 个进程。

**表现**：32 进程/机 ≈ 33 ep/h，远低于预期的 8 进程 × 60 ep/h。

**原则**：GPU 密集型任务先用 1 worker/GPU 测基线速度，再逐步加到 2、4 观察是否线性提升。不同 task 复杂度不同，不能一刀切。

## 3. 队列参数修改需要重建队列文件

**问题**：修改 `BATCH_SIZE` 后，`init_queue.py` 检测到队列已存在直接跳过，worker 仍然拿到旧的大 batch。

**原则**：修改 batch-size 后必须删除旧队列重建。代码中的"已存在则跳过"逻辑是为了断点续传，不是为了参数热更新。

## 4. 残留 cache 导致数据完整性错误

**问题**：渲染中途 crash，cache 目录残留不完整的 pkl 文件。下次重新渲染时 `merge_pkl_to_hdf5_video` 发现编号不连续而崩溃。

**解决**：
- 重启前清理 `.cache` 目录
- 代码层面：遇到不连续 pkl 时自动清理 cache 并抛异常，依赖 HDF5 存在性检查触发重试

**原则**：任何可能中断的流程，其中间产物目录在重启时应被视为不可信。要么启动前清理，要么运行时校验。

## 5. 进度监控应基于最终产物而非中间状态

**问题**：基于 queue batch 状态的监控显示全是 0（batch 未全部完成就不算 done），用户无法感知实际进展。

**解决**：改为直接数磁盘上的 HDF5 文件数量。

**原则**：监控指标应该反映用户关心的最终结果（文件数），而非系统内部状态（batch 状态）。

## 6. 跳过已完成工作是断点续传的核心

**问题**：stale batch 被 reclaim 后重新渲染已有的 episode，文件被覆盖但数量不增长。

**解决**：渲染前检查 `episode{N}.hdf5` 是否存在，存在则跳过。

**原则**：幂等性。任何 worker 在任何时候拿到任何 batch，都应该只做"尚未完成的部分"。检查最终产物是否存在是最可靠的判断方式。

## 7. 非阻塞锁用于队列认领，阻塞锁用于低频操作

**设计**：
- `claim_batch()`：`LOCK_NB`，拿不到就跳过下一个文件 → 不阻塞
- `mark_done()`：`LOCK_EX` 阻塞，但每个 batch 完成才调用一次 → 频率极低

**原则**：热路径用非阻塞 + 跳过/重试；冷路径可以用阻塞锁但要确保锁持有时间极短。

## 8. 多集群共享存储需要隔离

**问题**：两个集群的 barrier 文件、log 文件互相覆盖。

**解决**：`CLUSTER_ID` 隔离 barrier 目录和 log 文件名。任务不重叠时队列天然隔离。

**原则**：共享存储上的所有"协调文件"都需要 namespace 隔离机制。
